## 📦 目标

让查数列表和 CSV 显示中文列名，让生成的 SQL 可以逐项审查表、字段、过滤和关联。缩短第 ④ 步发给模型的文本，同时保留决定业务口径所需的证据。

## 📖 讲透

本机专题库历史中，有 5 轮走到第 ④ 步。它的中位耗时是 6.83 秒，模型请求的中位耗时是 6.83 秒，累计模型请求耗时占该阶段的 99.8%。同批的需求解析和 SQL 生成分别是 4.17 秒、1.65 秒。样本中无方案输出重试和上溯。

11 月 2 日的模拟库 C 组有 55 次规划调用，单次中位输入 14,467 tokens、输出 586 tokens、耗时 3.83 秒。55 次里没有输出校验重试，4 轮发生上溯。正常规划需要读取候选表、血缘、同源字段对比、关联路径和样例，再生成包括用表、字段、关联与口径说明的 JSON。用 ETL 类比，打开的是整个查数任务的设计依据，产出的是可执行 SQL 的前置设计。

## 🔧 选型

- 展示阶段按 SQL 的作用域追溯字段来源，结合数据字典补中文说明。计算列使用贴合本次口径的中文别名，必要时依据计算方式和来源字段补展示名。
- 规划提示词合并重复说明。相同方向、键、对应关系和依据的关联步骤只展开一次，其他路径以编号引用，每条路径的发散信息照常提供。
- 方案 JSON 省略空项，过滤、关联和排序已经给出结构化依据时可省略该字段的重复用途说明。口径、用表依据、有实际用途的关联与溯源说明照常输出。

## 💡 可迁移

先把总耗时拆成准备数据、远程调用和返回验证，类似拆开看 ETL 调度等待、数据库执行和结果落表。对同一批输入做对照，先量消息大小，再用同一模型和题库看耗时与结果正确率。

55 次离线同输入对照中，最终版规划消息中位长度由 28,871 字符降至 25,671 字符，减少 11.1%。51 轮回放使用原模型回复，状态全部一致。离线回放测量输入大小和固定回复下的流程行为。

首轮真实模型评估发现 3 道题在应反问时沿用了样例的默认口径，另有 1 道明细题将编号用作名称过滤。复测版本明确区分汇总范围和口径范围，要求口径不明时反问，并写清编号应与编号字段比较。

## 👨‍💻 代码

- `nl2sql/sql_presentation.py` 补中文 SQL 注释，按列位置生成 `column_labels`，检查带注释 SQL 能解析回同一棵语法树。
- `nl2sql/workflow.py` 在静态校验通过后处理展示 SQL。追问送给模型的底稿去掉展示注释。
- `web/src/components/ExecTable.tsx` 用展示名渲染表头并导出 CSV，兼容缺少 `column_labels` 的旧会话。
- `prompts/nl2sql.py` 明确最终列的中文别名，精简规划提示词及重复的关联路径证据。

## ⚠️ 常见坑

- CTE 或关联查询里，同名字段可能来自不同实体表。按 SQL 作用域和列位置匹配，避免用英文名全局查字典后串列。
- 执行结果为空时也保留中文表头。缺少可识别中文名称时，用中文列号和数据库原始列名提示。
- 注释改写须通过语法树往返校验。无法无损回读时保留可用的原 SQL。
- 全量离线测试 2,045 项通过，前端构建通过。Chrome 验证了有数据、空结果和旧会话。37 条模拟库标准 SQL 带注释后逐条通过静态校验，返回列及数据一致。

### 补测模型的优先顺序

用户指定按 `qwen3.8-max-0902`、`deepseek-v4.1-flash`、`deepseek-v4.1-flash-1017`、`kimi-k3.1-pro` 的顺序使用，额度耗尽后再切换。用合成请求探测项目的百炼连接，前两款返回 `400 Arrearage`，后两款返回 `403 AccessDenied.Unpurchased`。百炼备用连接在首款模型返回 `401 invalid_api_key`。待连接恢复后，从已有 80/367 道配对的记录续跑，保证同一道题的改前、改后用同一型号。

用户通知额度恢复后，按原顺序探测两轮，项目连接仍返回同样的错误。续跑脚本已用离线试运行核对 80 道已配对、287 道待配对。脚本按型号留存两版逐题记录，只有同题两版用同一型号完成时才计为配对。当前进度仍为 80/367。
